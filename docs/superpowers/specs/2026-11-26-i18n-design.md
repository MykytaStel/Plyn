# Plyn i18n: Ukrainian + English UI

Status: approved · 2026-11-26

## Intent

Add an English interface next to the Ukrainian one, switchable in Settings. Today this is "just a language switch" for people who prefer English. Later Plyn will enter the English-speaking market, so the English UI must be able to become a native-quality product **without reworking the architecture**: native copy, an English sample text, English onboarding.

Product principle (see `AGENTS.md`): calm and uncluttered beats feature-rich, and quality beats speed.

## Key insight: UI language ≠ content language

The interface language and the language of the text being read are independent. A Ukrainian user reads English articles, and an English user may import a Ukrainian book. This change is about **UI chrome only**. Content handling already works per text and must stay that way:

- TTS picks a voice from the card's content (`detectLanguage` in `services/speech/tts.ts`).
- Fonts fall back per glyph (Latin dyslexia fonts + Cyrillic Andika/Fixel).
- The splitter knows abbreviations in both languages.

One new consequence: the reader card uses `hyphens: auto` (`tokens.css:743`), and browsers hyphenate according to the `lang` attribute. When `<html lang>` follows the UI language, the reader card must set its own `lang` from the detected **content** language. Otherwise Ukrainian text in an English UI gets English hyphenation rules.

## Goals

1. Every user-visible UI string is translatable: visible text, `aria-label`, `title`, `placeholder`, toasts, confirm dialogs, errors, achievements, preset hints, onboarding (including its sample text), and Markdown export headings.
2. A missing translation is a **build error**, not a runtime surprise.
3. Plurals, numbers and dates are correct per locale. Ukrainian needs one/few/many forms (1 картка, 2 картки, 5 карток).
4. Switching language is instant (no reload), persists, and works offline.
5. No new runtime dependencies, and a negligible bundle increase.

## Non-goals (now)

- Translating user content.
- More than two languages. The architecture must not block adding more, but there's no tooling for it now.
- A translation platform or string-extraction tooling.
- English marketing, a landing page, a store listing, or a localized PWA manifest. The manifest stays as is (`name` "Plyn…", `lang: "uk"`) until the market launch.
- RTL support.

## Anti-goals (failure even if it "works")

- A language flag or switch added to the main screens. It lives in Settings only.
- A mixed-language UI. Ship only when 100% of strings are migrated.
- Literal, machine-sounding English. English copy is written natively in Plyn's tone: calm, short, "you", no pressure or guilt.
- Any regression in the existing Ukrainian copy.
- Reader behaviour that depends on the UI language (hyphenation, TTS, fonts).

## Approaches considered

| | Approach | Trade-off | Decision |
|---|---|---|---|
| **A** | Own typed dictionaries + `Intl` | 0 deps, ~1 KB, strongest type safety, full control. Translator tooling must be built if we ever reach 5+ languages. | **Chosen** |
| B | i18next + react-i18next | Industry standard and ecosystem. Adds ~15–20 KB and configuration, weaker typing. Overkill for 2 languages. | Rejected |
| C | Lingui (macros + extraction) | Best for many languages and translators. Needs Vite macro setup, the most infrastructure. | Rejected |

Why A: for two languages, the value is in copy quality, not in a library. Flat messages with `{placeholder}` interpolation port cleanly to B or C if Plyn ever needs many languages.

## Design

### Locale and settings

- `type Locale = 'uk' | 'en'`. Add `language: Locale` to `UserSettings`. It is persisted through the existing `plyn_settings_v1` (load already merges defaults, so no new key is needed).
- **Default language is always `'uk'`** (owner's decision). There is no browser-language detection. English is reached only through Settings. Existing users get `'uk'` through the defaults merge. Revisit auto-detection at the English market launch: it's a one-line change in `DEFAULT_SETTINGS` / `loadUserSettings`.
- `syncDom` also sets `document.documentElement.lang = settings.language`.

### Dictionaries

```
src/i18n/
  locales/uk.ts   source of truth, `export const uk = {...} as const`
  locales/en.ts   `export const en: Messages = {...}`
  types.ts        `Messages` = deep shape of `uk` with every leaf widened to string / PluralForms
  index.ts        useMessages(), format(), plural(), formatNumber(), formatDate(), getMessages(locale)
  i18n.test.ts
```

- Messages are nested by feature: `common`, `library`, `reader`, `settings`, `onboarding`, `thoughts`, `bookmarks`, `achievements`, `presets`, `errors`, `export`.
- Components read typed objects: `const m = useMessages(); m.reader.done.title`. Autocomplete and type checking work and there are no stringly-typed keys.
- Interpolation: `format(m.reader.done.summary, { count })`, with `{name}` placeholders.
- Plurals: a leaf may be `PluralForms = { one?: string; few?: string; many?: string; other: string }`. `plural(m.common.cards, count, locale)` selects the form with `new Intl.PluralRules(locale)`. Ukrainian entries must define `one`, `few`, `many` and `other`, enforced by a test.
- Numbers and dates go through `Intl.NumberFormat` and `Intl.DateTimeFormat` with the current locale. Remove the hard-coded `toLocaleString('uk-UA')`.
- `useMessages()` subscribes to `useSettingsStore(s => s.language)`, so switching re-renders immediately.
- Both dictionaries are bundled. They are small, and lazy loading isn't worth the complexity offline.

### Keeping `src/core/` pure

Core must not import i18n. Core code that currently returns Ukrainian text changes to return data, and the UI maps it to messages:

| Today | Change |
|---|---|
| `achievements.ts`: `title`, `description` | Keep only `id`, `target` and `getProgress`. Text lives in `m.achievements[id]`. Stored `unlockedIds` are unaffected. |
| `readingPresets.ts`: `hint` | Text lives in `m.presets[id].hint` (and `title` if present). |
| `weeklyActivity.ts`: `SHORT_DAYS_UK` | Return dates. The UI formats weekdays with `Intl.DateTimeFormat(locale, { weekday: 'short' })`. |
| `bookmarksMarkdown.ts`: headings | Take a `labels` argument (`bookmarks`, `card`, `note`). Export uses the UI language. |
| `markdown.ts` `deriveTitle`: `'Без назви'` | Take a `fallback` argument. |
| Parser/backup errors (`epub.ts`, `pdf.ts`, `backup.ts`) | Throw `PlynError` with a `code`. The UI maps codes to `m.errors[code]`. |

Regexes containing Cyrillic (anchor, reading stats, TTS, splitter) are content logic, not UI. Leave them.

### Worker `/api/extract`

Return a stable `code` (`invalid_request`, `invalid_url`, `unsupported_protocol`, `blocked_host`, `upstream_error`, `no_article`, `network_error`) and keep the current Ukrainian `error` field for one release, so that clients still running an old cached service worker keep working. The client shows `m.errors.extract[code]` and falls back to `error`.

### Reader content language

`ReaderView`/`CardSlide` set `lang` on the card element from the detected content language. Export a shared `detectContentLanguage(text): 'uk' | 'en'` from one place, and make TTS reuse it, so hyphenation and TTS always agree.

### Settings UI

One row in Settings, placed last (it's rarely changed): label "Мова · Language" and a segmented control **Українська | English**. Languages are always shown by their own names, whatever the current locale.

### Copy

- English copy is written as native product copy in the same tone, not translated word for word. Keep sentence lengths similar so layouts don't break.
- English sample text for onboarding: a short original passage on the same theme ("wall of text").
- Keyboard shortcut hints stay dual-layout. Hints in the English UI mention Latin keys only.

### Guard against regressions

A Vitest test (Node, `fs`) scans `src/features/**/*.tsx` and `src/core/**/*.ts` (excluding tests and comments) and fails if it finds Cyrillic inside string literals or JSX text. The `src/i18n/` folder and the known content regexes are allow-listed. This keeps new hard-coded Ukrainian strings out after the migration.

## Testing

- `i18n.test.ts`: plural selection for uk (1, 2, 5, 11, 21, 22, 25, 111) and en (1, 2); `format` interpolation; every `PluralForms` in `uk` has `one/few/many/other`; uk and en have identical key sets at runtime (a belt-and-braces check on top of the type check).
- Settings: a saved settings object without `language` loads as `'uk'`, and a round-trip with `'en'` persists.
- Core changes (achievements, presets, weeklyActivity, bookmarksMarkdown, deriveTitle): update the existing tests.
- Manual pass in both languages on mobile width: library, reader, settings, onboarding, every sheet, error states, and the long-word layout (German-length English words are not a concern, but long Ukrainian ones are).

## Rollout

1. Infrastructure (`src/i18n`, settings field, `html lang`, reader `lang`), with `en.ts` initially a copy of the keys.
2. Migrate feature by feature: library → reader → settings → onboarding → sheets → core refactors → worker codes.
3. Turn on the Cyrillic-literal guard.
4. Write the English copy and run a copy review pass.
5. Release as one version (no partially translated UI in production).

## Left to the builder

- Exact message key names and nesting within each feature.
- Whether `format`/`plural` are standalone functions or methods on a small `i18n` object.
- `PlynError` shape details and the full list of error codes for parsers and backups.
- Implementation of the guard test (regex or a small tokenizer), as long as it ignores comments.

## Decisions log

- Approach A (own typed dictionaries + `Intl`), chosen by the owner.
- Default language is always Ukrainian, chosen by the owner. Auto-detection is deferred to the English market launch.
- Builder's calls, made in this document: the Settings-only switch placed last, endonym labels, both dictionaries bundled, the worker keeping `error` for one release, the reader card `lang` taken from content, and the Cyrillic-literal guard test.
